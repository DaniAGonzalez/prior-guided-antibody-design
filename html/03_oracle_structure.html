Notebook 03 — The Structure Oracle: TAP-style developability from predicted 3D structure

Where this sits. The oracles so far (notebook 02) score the *sequence*. But some developability
liabilities are only visible in *3D structure* — hydrophobic or charged patches on the folded
surface. This notebook predicts the antibody structure and computes TAP-style metrics
(Therapeutic Antibody Profiler, Raybould et al. 2019), then uses TAP as a final structural filter
on top of the sequence oracles. This is the multimodal (sequence + structure) part of the evaluator.

**Background from zero**S2 - antibody structure, TAP, surface patches
**Structure prediction**S3 - ABodyBuilder2 / NanoBodyBuilder2
**TAP metrics**S4 - the five flags, and how each is computed
**Design decision: two options**S5 - full Fv (paired VL) vs VH-only

1. Question

A CDRH3 can score perfectly on sequence oracles and still fold into a shape with an exposed
hydrophobic patch that drives aggregation. Sequence alone cannot see this.

> **Does a structural developability score (TAP) add information the sequence oracles miss, and can
> we use it as a final filter to reorder otherwise-equal candidates?**

Hypothesis. If structure carries independent signal, the TAP score should be uncorrelated
with the sequence reward S(x) on a shortlist of good sequences. If so, TAP is a meaningful second
modality, not a redundant re-scoring.

2. Background from zero

Antibody structure. The variable region (Fv) is the two domains that do the binding: VH
(heavy) and VL (light), each an immunoglobulin fold (a beta-sandwich) with the CDR loops at one
tip. The framework holds the loops in a fixed geometry; the CDRH3 loop we design sits at the very
tip of the binding site.

Why predict structure at all? Some developability risks are *spatial*. Two hydrophobic residues
far apart in sequence can be neighbors on the folded surface, forming an aggregation-prone patch.
You need the 3D coordinates to see it.

TAP (Therapeutic Antibody Profiler). A set of five structure-derived flags that correlate with
clinical developability:
- Total CDR length - longer loops = more liability surface.
- PSH (Patches of Surface Hydrophobicity) - hydrophobic patch area in the CDR vicinity.
- PPC / PNC (Patches of Positive / Negative Charge) - charged patches near the CDRs.
- SFvCSP (Structural Fv Charge Symmetry Parameter) - charge complementarity between VH and VL
(needs both chains).

Each metric has green / amber / red thresholds from the paper. We turn the five flags into a single
[0,1] score (green=1, amber=0.5, red=0).

Honest note (established project constraint). The official TAP code is not public. This is
a TAP-style reproduction from the paper's method description, not the exact tool. We say so
wherever TAP numbers appear.

3. Structure prediction — ABodyBuilder2 / NanoBodyBuilder2

ABodyBuilder2 (ImmuneBuilder, Abanades et al. 2023) is a fast deep-learning antibody structure
predictor. It takes VH (and optionally VL) sequences and outputs 3D coordinates, refined with a
short OpenMM energy minimization. It is an ensemble of 4 models; loading the weights is slow (~11
min, one-time) but a single prediction is fast (~3 s).

A practical detail (interview-relevant). The package ships expecting to write its downloaded
weights *inside its own install directory*, which is read-only in a sandboxed environment. The fix
is to pass an explicit writable weights_dir. Same pattern as AbLang2 in notebook 02 — deployment
plumbing that bites in production.

*This notebook loads the cached predictions/metrics (structure prediction was run once) so it
executes in seconds; the prediction code is shown for reference.*

4. TAP metrics — how each is computed

The data flow from a PDB structure to the five TAP flags, which is the part worth understanding in
detail:

1. Number the residues (ANARCI, IMGT scheme). ANARCI assigns every residue an IMGT number so we
can locate the CDRs by definition (IMGT CDR ranges: CDR1 27-38, CDR2 56-65, CDR3 105-117). This
is how we know *which* residues are "in the CDR vicinity" independent of sequence length.
2. Compute solvent accessibility (freesasa). Per-residue SASA (solvent-accessible surface area)
tells us which residues are actually *exposed* on the surface — only exposed residues can form a
liability patch.
3. Score patches over the CDR vicinity (CDR residues +/- 2 anchor residues):
- PSH = sum over vicinity of Kyte-Doolittle hydrophobicity * (SASA/100) — exposed
hydrophobic area.
- PPC / PNC = same but weighted by positive / negative formal charge (R,K = +1; D,E = -1;
H = +0.1).
4. SFvCSP = net_charge(VH) * net_charge(VL) — charge symmetry between the two chains (only
defined when both chains are present).

# --- Turn the five raw TAP metrics into a single [0,1] score via green/amber/red flags ---
# Thresholds from the TAP paper (green = healthy, amber = borderline, red = flagged).
# Each metric -> 1.0 (green) / 0.5 (amber) / 0.0 (red); tap_score = mean over the applicable metrics.
TAP_FLAGS = {
    "total_cdr_len": dict(green=(0,55),  amber=(0,60)),      # longer CDRs = more liability surface
    "PSH":           dict(green=(-40,0), amber=(-50,10)),    # too-hydrophobic surface patches
    "PPC":           dict(green=(0,2.0), amber=(0,3.0)),     # positive charge patches
    "PNC":           dict(green=(0,3.0), amber=(0,4.0)),     # negative charge patches
    "SFvCSP":        dict(green=(-10,50),amber=(-20,60)),    # VH/VL charge symmetry (Fv only)
}
def flag_score(metric, val):
    if val is None: return None
    g, a = TAP_FLAGS[metric]["green"], TAP_FLAGS[metric]["amber"]
    if g[0] <= val <= g[1]: return 1.0        # green
    if a[0] <= val <= a[1]: return 0.5        # amber
    return 0.0                                 # red

# recompute tap_score from the raw metrics to show the flag logic explicitly (matches cached value)
ex = tap["A"][0]
flags = {m: flag_score(m, ex.get(m)) for m in TAP_FLAGS}
print("example sequence raw metrics:", {m: (round(ex[m],2) if ex.get(m) is not None else None) for m in TAP_FLAGS})
print("per-metric flag scores:      ", flags)
print(f"tap_score = mean of flags = {np.mean([v for v in flags.values() if v is not None]):.3f}  "
      f"(cached {ex['tap_score']:.3f})")

5. Design decision — full Fv vs VH-only

Our project is heavy-chain only, but TAP's SFvCSP needs both VH and VL. Two ways to handle this:

- Option A (full Fv). Pair the designed VH with a fixed human germline VL, fold the complete Fv,
and compute all five metrics. Gives the real SFvCSP but adds an arbitrary VL.
- Option B (VH-only). Fold VH alone with NanoBodyBuilder2, compute the four VH-derived metrics,
skip SFvCSP.

We ran both and compared, rather than guessing which is right.

# --- Compare the two options across the 12-sequence batch ---

    vals = [x[m] for x in tap[opt] if x.get(m) is not None]

project's structure oracle can run either.

6. The cascade — TAP as a final structural filter

This is how structure enters the pipeline in practice: a two-stage filter. Sequence oracles are
cheap, structure is expensive, so we screen on sequence first and only fold the survivors.

1. Stage 1 (sequence): score all 120 generated loops with S(x), keep the top 15.
2. Stage 2 (structure): fold those 15, compute TAP, keep those passing TAP >= 0.8.

The key question: does stage 2 *do anything*, or does it just pass everything stage 1 selected?

# --- The cascade: sequence shortlist -> structural TAP filter ---
fc = json.load(open("final_filtered_candidates.json"))
sl = fc["shortlist_scored"]                       # the 15 top-S(x) loops, each also TAP-scored
S_seq = np.array([x["S_seq"] for x in sl]); TAP = np.array([x["tap_score"] for x in sl])
n_pass = int((TAP >= fc["tap_pass"]).sum())
corr = np.corrcoef(S_seq, TAP)[0,1]
print(f"stage 1: 120 loops -> top {fc['stage1_K']} by S(x)")
print(f"stage 2: TAP >= {fc['tap_pass']}  ->  {n_pass}/{len(sl)} pass")

top = fc["final_ranked"][0]
