Notebook 05 — Reinforcement Learning loop (REINVENT for antibody CDRH3)

antibody language model and *nudges* it, with reinforcement learning, toward generating CDRH3

you are new to antibodies, read the Background section first; nothing later assumes prior

1. The question

We have a generator (IgLM, notebook 01) that already produces plausible antibody CDRH3 loops,
and oracles (notebooks 02, 03, 06) that score any loop on developability and binding.

> **Can reinforcement learning shift the generator's output distribution toward
> higher-scoring loops, and can we do it without the model collapsing into degenerate
> sequences that "game" the score?**

Two things are under test at once:

1. Optimization — does the policy-gradient update actually move the reward? (Sections 5, 9)
2. Regularization — does the frozen-prior term keep the agent antibody-like? (Section 7)

Neither answer is obvious in advance. Our developability oracles are already near-saturated on
IgLM's output (the model was trained on real human antibodies, so it starts "good"), which may
make the RL signal weak. We *measure* this rather than assume it.

2. Background (from zero)

2.1 What is an antibody, and what is a CDRH3?

An antibody is a Y-shaped protein the immune system uses to recognize targets ("antigens").
Each arm of the Y is built from two protein chains, a heavy chain and a light chain. The
tip of each arm actually touches the antigen; it is the variable region, so called because
its sequence varies enormously between antibodies (that variety is how your immune system
recognizes almost anything).

Within the variable region, most of the sequence is a conserved scaffold, the framework,
nearly identical across antibodies. Sitting on the framework are three short hypervariable loops,
the CDRs (Complementarity-Determining Regions): CDR1, CDR2, CDR3. The third loop of the heavy
chain, CDRH3, is the most variable of all and usually contributes the most to binding. It is
built by a random genetic recombination process, so it has no fixed length or sequence.

This is why the project optimizes only CDRH3. We keep the framework fixed (it is the stable
scaffold) and rewrite only the loop that matters most for function:

`
framework ... C-A-R-[ CDRH3 ]-W-G-Q-G ... framework
^^^^^^^^^^^
positions 98..idx, the only region we touch
`

2.2 What is IgLM, and what does "prior" mean here?

IgLM is a GPT-style language model trained on hundreds of millions of real antibody
sequences. Given a framework with a masked CDRH3, it *infills* a plausible loop, like an
autocomplete that has read every antibody ever sequenced. Because it learned from real
antibodies, its output is already human-like and developable, which is both a blessing (good
starting point) and a curse (little room to improve, the "saturation" mentioned above).

In RL terms this pretrained model is our prior: our belief, before optimization, about what a
"normal" antibody looks like. We make a second, trainable copy, the agent; only the agent
learns. The prior stays frozen as a reference.

2.3 Why two copies? The leash intuition

With one model rewarded for high scores, it would quickly find cheats: degenerate loops that
happen to score well but are not real antibodies (Section 7 shows the mechanism). The frozen
prior prevents that. The update does not say "maximize reward"; it says **"move toward higher
reward, but stay close to what the prior considers a normal antibody."** The prior is a leash.
This is the central idea of REINVENT and the reason it works where naive reward-maximization
fails.

3.1 The differentiable span log-likelihood

IgLM's own log_likelihood returns a detached number, useless for training. We need the
log-probability of the CDRH3 span *as a differentiable tensor* so gradients flow into the agent.
IgLM's infill token layout is:

`
[HEAVY][HUMAN] framework_left [MASK] framework_right [SEP] <CDRH3 span> [CLS]
^^^^^^^^^^^^^^^^^^^^
the model predicts this
`

A subtle detail we verify: the scored span must include the final [CLS] token, or the mean
disagrees with IgLM's native value.

# --- The differentiable log-likelihood of the CDRH3 span. This is the quantity RL optimizes,
#     and the part an interviewer will probe hardest: which tensor, which axis, which indices. ---

def build_infill_ids(full_seq):
    """Recreate IgLM's exact infill token layout so our log-prob matches the model's own.
    Token stream (IgLM is a decoder-only GPT2LMHeadModel):
        [HEAVY][HUMAN] framework_L [MASK] framework_R [SEP] <CDRH3 span> [CLS]
    The model generates the CDRH3 autoregressively AFTER the [SEP] separator; [CLS] is the EOS."""
    end   = full_seq.index(CLOSING); resid = list(full_seq)
    masked = resid[:INFILL_START] + ["[MASK]"] + resid[end:] + ["[SEP]"]
    span   = list(full_seq[INFILL_START:end])
    toks   = ["[HEAVY]", "[HUMAN]"] + masked + span + [tok.cls_token]
    return torch.tensor([tok.convert_tokens_to_ids(toks)], device=dev), toks.index("[SEP]"), len(toks)

def span_logp(model, full_seq, requires_grad):
    """Sum of per-token log-probs over the generated CDRH3 span."""
    ids, es, L = build_infill_ids(full_seq)          # es = index of [SEP]; span lives at es+1 .. L-1
    ctx = torch.enable_grad() if requires_grad else torch.no_grad()
    with ctx:
        # logits come from the LM head (final layer), shape [seq_len, vocab_size].
        # log_softmax over dim=-1 (the VOCAB axis) turns them into per-token log-probabilities.
        logp = F.log_softmax(model(ids).logits[0], dim=-1)
        # Standard next-token shift: position t's logits predict token t+1. So to score the span
        # tokens (ids at es+1 .. L-1) we read the logits at positions es .. L-2, i.e. logp[es:L-1],
        # and gather the log-prob of the ACTUAL next token (teacher forcing).
        # IMPORTANT: the span runs to L (includes the final [CLS]/EOS). Dropping it makes our mean
        # disagree with IgLM's native log_likelihood — the closing token carries real probability mass.
        val  = logp[es:L-1, :].gather(1, ids[0, es+1:L][:, None]).sum()
    return val, (L - 1 - es)                          # (summed log-prob, number of scored tokens)

# --- Fidelity check: our reimplementation must equal IgLM's own log_likelihood to <1e-3, or every

4. The reward and the REINVENT update

4.1 The reward

Our reward for a sequence $x$ is the weighted developability score $S(x) \in [0,1]$ (notebook 04):

$$S(x) = 0.50\,\text{humanness}(x) + 0.30\,\text{liability}(x) + 0.20\,\text{physchem}(x)$$

Design decision, weighted sum vs. alternatives. We chose a fixed weighted sum. Alternatives:
*Pareto/multi-objective* (keeps a front instead of one scalar; more principled but heavier and
awkward for a scalar policy-gradient reward, rejected for a first study) and a *learned reward
head* (the multimodal extension planned for notebook 07, rejected here because it needs labeled
data we build later; the weighted sum is the honest baseline it will be compared to). Weights
are tunable: humanness gets the most weight because it had the widest spread on the reference
pool (notebook 04), so it carries the most signal.

4.2 The augmented likelihood, the heart of REINVENT

REINVENT does not maximize reward directly. It defines an augmented log-likelihood, the
prior's opinion *shifted* by the reward, and trains the agent to match it:

$$\log P^{*}(x) = \log P_{\text{prior}}(x) + \sigma \cdot S(x), \qquad
\mathcal{L}(x) = \big(\log P_{\text{agent}}(x) - [\log P_{\text{prior}}(x) + \sigma\, S(x)]\big)^{2}$$

- $\sigma = 0$: target is the prior. Agent pulled toward prior, no optimization, max leash.
- larger $\sigma$: target shifts up for high-reward sequences, agent raises their probability,
more optimization, looser leash.

$\sigma$ is the single most important knob (Section 6 sweeps it). The squared-error form and
the prior term are fixed (they define REINVENT).

# --- The three building blocks of one RL step: sample from the policy, score, update. ---

def sample_agent(agent_iglm, n, seed=None):
    """Sample n sequences from the current policy by infilling the CDRH3 (top_p=1, temperature=1
    by default -> pure ancestral sampling from the model distribution).
    NOTE: IgLM.infill returns the COMPLETE sequence (framework + new CDRH3), not just the loop.
    A bug caught in development re-wrapped it in the framework again -> malformed double-framework
    sequences. Use the return value directly."""
    if seed is not None: torch.manual_seed(seed); np.random.seed(seed)
    return agent_iglm.infill(PARENT, "[HEAVY]", "[HUMAN]",
                             infill_range=(INFILL_START, PARENT.index(CLOSING)), num_to_generate=n)

def score_S(full_seq, guard=True):
    """Reward: weighted developability score in [0,1] (humanness .50 / liability .30 / physchem .20)."""
    c = extract_cdrh3(full_seq)
    if guard and len(c) < 4: return 0.0     # IMPORTANT: length guard blocks reward-hacking (Section 7)
    if len(c) < 1: return 0.0
    return 0.50*oracles.humanness_oracle(full_seq) + 0.30*oracles.liability_oracle(c) + 0.20*oracles.protparam_oracle(c)

def reinvent_step(agent, opt, batch_seqs, sigma, reward_fn):
    """One REINVENT update (Olivecrona et al. 2017). NOT a vanilla policy gradient: instead of
    maximizing E[reward], we define a target 'augmented likelihood' and regress the agent onto it.
        target(x)  = logP_prior(x) + sigma * reward(x)
        loss(x)    = ( logP_agent(x) - target(x) )^2        # squared error, averaged over the batch
    sigma sets how far the target is pulled above the prior for high-reward x."""
    opt.zero_grad(); total=0.0; a_lps=[]; p_lps=[]; Rs=[]
    for seq in batch_seqs:
        R = reward_fn(seq)
        a,_ = span_logp(agent, seq, requires_grad=True)                        # agent branch: gradients ON
        with torch.no_grad(): p,_ = span_logp(prior, seq, requires_grad=False) # prior branch: frozen, no grad
        total = total + (a - (p + sigma*R))**2                                 # per-sequence squared error
        a_lps.append(a.item()); p_lps.append(p.item()); Rs.append(R)
    (total/len(batch_seqs)).backward()
    torch.nn.utils.clip_grad_norm_(agent.parameters(), 1.0)   # IMPORTANT: global-norm grad clip = 1.0 (stability)
    opt.step()
    # kl_proxy is NOT the true KL divergence. It is a cheap directional proxy: the gap between the
    # prior's and agent's mean log-likelihood on the agent's own samples. >0 = agent still near prior,
    # <0 = agent has moved probability mass away from the prior. Enough to see divergence trend.
    return dict(loss=(total/len(batch_seqs)).item(), mean_R=float(np.mean(Rs)),
                kl_proxy=float(np.mean(p_lps)-np.mean(a_lps)))

7. Ablation 2 — the length guard and the reward-hacking mechanism

score_S has a guard:

`python
if guard and len(cdrh3) < 4:
return 0.0 # degenerate short loops get zero reward
`

Why? span_logp sums log-probs over the CDRH3. Fewer tokens means fewer negative terms, so
a shorter loop can reach a higher (less negative) summed log-probability — the very quantity the
agent maximizes. Combined with oracles that still return a decent score for a degenerate loop,
this creates an incentive to collapse the CDRH3 toward nothing. That is reward hacking:
optimizing the letter of the reward while violating its intent.

We tried to induce the collapse dynamically (aggressive sigma=40, lr=1e-4, 3 seeds). It did
not trigger in a reasonable step budget: the IgLM prior anchors the agent to full-length,
framework-consistent loops, so the agent never wandered into the short-loop region on its own
(guard-on and guard-off gave identical curves). Rather than burn hours chasing a stochastic
event, we demonstrate the *mechanism* directly and deterministically.

than with a hard floor. Seeing the raw mechanism is the point.

8. Ablation 3 — why are the curves so spiky? (batch size)

You asked earlier why the reward curves have so many peaks and whether that is normal. **It is,
and here is the proof.** Each plotted point is the mean reward of a *fresh batch of stochastically
sampled sequences*. With a small batch that mean is a noisy estimate, so the curve jumps even
when the policy barely changes.

We run the identical loop at batch $\{8, 16, 32\}$, 3 seeds each, and measure step-to-step
roughness (mean absolute change). Hypothesis: roughness scales like $1/\sqrt{\text{batch}}$,
a sampling effect, not optimizer instability.

9. Positive control — a reward that *must* move

The developability reward was flat: broken loop, or saturated oracle? We disentangle with a
positive control, replacing the reward with the tyrosine fraction of the CDRH3 — cheap,
unambiguous, and with obvious headroom (the starting pool has a low tyrosine fraction). If the
RL machinery is correct, this reward must rise. **This is the single most important sanity check
in the project.**
